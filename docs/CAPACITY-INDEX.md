# Capacity Index

> A public, reproducible catalogue of how much state real Soroban designs can hold,
> and which limit stops them. Each entry is a scenario, a certificate, and a
> command.

---

## 1. Why an index and not just a tool

A tool proves the method. An index proves the **method matters**.

One certificate is an anecdote: "this contract dies at 1,318". Twenty certificates
from different designs, measured the same way, are a map of the design space — and a
map is what turns a measurement into a decision:

- *Instance storage is the wrong default for registries* becomes a claim with a
  number behind it.
- *Batch payouts top out near 100 recipients* stops being folklore.
- *A token's transfer cost is flat in holder count* becomes a fact you can cite.

The index is also the project's long-term asset. Code can be rewritten; a consistent
public dataset of capacity measurements under named protocol versions cannot be
recreated retroactively.

---

## 2. What counts as an entry

| Requirement | Detail |
|---|---|
| A real contract | deployed or deployable, with WASM bytes and a hash |
| A declared design | what the population is and how it is stored |
| A scenario | committed, runnable, with no hidden setup |
| A certificate | produced by the released tool, `verify`-clean |
| A named limit snapshot | the protocol state at measurement time |
| Provenance | who ran it, when, on what |
| Permission | the contract's author is credited; nothing proprietary is exposed |

An entry that cannot satisfy all seven is not published. There is no "preliminary"
category, because a preliminary number is the one that gets quoted.

---

## 3. Entry format

```text
index/entries/<org>-<contract>/
├── README.md            one page: design, result, what it means, reproduction
├── scenario.toml        the question
├── certificate.json     the answer
├── wasm.sha256          the bytes (hash and size; artifact built in CI)
└── notes.md             optional: caveats, contract quirks, author response
```

`index/index.json` is generated from these folders and contains only fields that
appear in the certificates plus the design summary. It is regenerated by
`headroom index --check` in CI, and a mismatch fails the build.

## 4. The first five entries

Chosen to cover the failure modes, not to flatter the tool.

| Entry | Design | Population | Expected binding limit | Why it is in the set |
|---|---|---|---|---|
| `registry-instance` | IDs in one instance `Vec` | registrants | entry size (65,536 B) | the canonical mistake |
| `registry-persistent` | one entry per registrant | registrants | write entries or none | the fix, measured |
| `escrow-open` | one entry per open escrow | concurrent escrows | entry size or none | the most common escrow design |
| `token-holders` | balance per holder | holders | none (flat cost) | the negative result |
| `payout-batch` | loop of transfers in one tx | recipients per tx | write entries (200) | the batch illusion |

Two of the five are expected to find no cliff. That ratio is the point: capacity
panics are sometimes wrong, and the index says so.

### Later entries (v1.0 target)

| Family | Example design | Interesting question |
|---|---|---|
| AMM | reserves + LP positions | does depth change cost per swap? |
| NFT collection | one entry per token | where does enumeration break? |
| DAO | proposals + votes per proposal | votes per proposal vs event budget |
| Subscription | billing schedule per subscriber | does a charge scale with subscriber count? |
| Order book | sorted price levels | contention on the best bid |
| Vesting | schedule per beneficiary | cliff date arithmetic at scale |
| Multi-sig | pending tx per owner | approval loop footprint |
| Marketplace | listings per seller | search-like reads |

## 5. What the index is not

- **Not a leaderboard.** A design with a higher `N*` is not "better"; it may be
  solving an easier problem. Entries are grouped by family, and the README says so at
  the top.
- **Not an audit.** A certificate says nothing about correctness, access control, or
  whether the contract should exist.
- **Not a performance benchmark.** Nothing here is about speed, latency or hardware.
- **Not comparable across protocol versions.** Each entry names its snapshot. A
  cross-version diff is published only as an explicit migration note.

## 6. Review process

1. **Author or contributor** opens a PR with the four files and a `verify`-clean
   certificate.
2. **CI** re-runs the scenario, compares certificates byte-for-byte, and checks the
   WASM hash against the declared artifact.
3. **A reviewer** reads `scenario.toml` and asks one question: *does this scenario
   model what the README says it models?* A scenario can be perfectly reproducible
   and still describe the wrong workload.
4. **The contract's author is mentioned**, with a two-week window to correct the
   design description. Silence is consent, but the mention is recorded.
5. **Merge** adds the folder; `index.json` regenerates in the same PR.

Reviewer checklist, in full:

- [ ] the population unit matches the design (not "users" when it means "entries")
- [ ] `preallocate` matches the claim being made
- [ ] `batch` is used where the real contract batches
- [ ] no limit overrides (indexed runs use pinned real settings)
- [ ] the binding limit is stated, not just `N*`
- [ ] the interval is stated
- [ ] the reproduction command is one line and works offline
- [ ] the entry says what would change the answer

---

## 7. Maintenance

Capacity is a claim with an expiry date. Each entry records the snapshot it was
measured under. When a protocol upgrade lands:

1. A new snapshot is added to `limits/`.
2. `headroom index --rerun` measures every entry under the new snapshot.
3. The diff is published as a release note, naming entries whose `N*` moved, by how
   much, and — more usefully — **entries whose binding limit changed**.

That last category is where the interesting findings live. A design whose binding
limit moves from entry size to write bytes has not just lost capacity; it has changed
its character, and the fix has changed with it.

---

## 8. Governance

- The index is append-only. Entries are superseded with a new dated folder, never
  edited in place, so a link to a measurement keeps meaning what it meant.
- A withdrawn entry stays visible with a reason. Deleting an inconvenient measurement
  is the failure mode this whole document exists to prevent.
- Conflicts are resolved by re-running: if two parties disagree about a design's
  capacity, both scenarios are published, and the difference is explained (usually a
  different population definition).
- No entry is accepted in exchange for anything. There is no sponsored tier.
